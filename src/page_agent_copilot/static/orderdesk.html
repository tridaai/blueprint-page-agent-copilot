Task library

The recurring jobs, kept as governed templates: a pattern with named slots, a note on when to use it, and a version. Instantiating one fills its slots and states the rendered text as an ordinary task — the planner derives the plan from that text, so a template never carries a plan of its own past the planner. Every version pins examples; a version whose examples no longer derive to their pinned shape is marked BROKEN here, by name and version. Publishing a new version is a supervisor act, recorded; old versions stay instantiable by name and version.

Roles

Who may do what is governed data, enforced by the shell at plan time, at confirmation, and again at execution. A plan is confirmed by a second person — never its planner — so to confirm a plan below, set the operator name above to a supervisor (s.hale). Role definitions are edited only by a supervisor, and every edit is recorded.

Operator directory

The directory is governed like the roles: names are enrolled, assigned a role, deactivated, and reactivated only by a supervisor, and every one of those acts is recorded in the roles audit. A deactivated name may perform no act at all — every gate refuses it — and it is never deleted, so the work it did stays attributable to it. The buttons below act as the operator named at the top of this screen.

Orphaned work

Unfinished work whose operator has been deactivated. It is never auto-reassigned and never deleted: a supervisor picks it up deliberately, as a recorded act, and the original planner stays on the task.

No orphaned work.

Operator report & attribution

Folded from the audit trail — never from counters. The attribution check scans every act in the trail: each actor must resolve to a directory name (active or deactivated) or to one of the shell's own components.

Amend the plan (before confirmation)

An amendment creates a new plan version, and the confirmation is then owed on that version — confirming the old text can never run the new one. A confirmed plan cannot be amended at all: reject it and state a fresh task.

Offline driver: deterministic, runs in the shell against the same records — it is not PageAgent. In-page agent: the real page-agent package running in this browser; it needs a configured model endpoint (PAGEAGENT_* settings) and fills the actual forms on these screens.

Resolve this discrepancy

A discrepancy has exactly two exits, both recorded. Spawn a corrective task — a new, linked task whose plan closes only the differences named below, confirmed and verified in the usual way — or, as a supervisor, accept the deviation with a reason. Accepting closes the task as DISCREPANCY_ACCEPTED; it never becomes VERIFIED, and the report below is never edited.

Execution failed — pick it up, run it again, or close it

The run stopped at the failed step. The steps before it stand as they landed — they are named in the attempt record below, and nothing is rolled back. Resume runs only the steps that never completed, after checking the completed work still stands and the rest of the plan's basis has not moved. Restart runs the whole plan again as a new attempt, and is refused once a step has created a record — a create is never run twice. Abandon closes the task as ABANDONED with a reason; the partial state stays on the records, named.
